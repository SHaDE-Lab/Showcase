# Cool Routes: example release of the routing method

Walking routes that trade a little distance for a lot less radiant heat. This folder is a **curated,
runnable, tested example release** of the method behind the
[Cool Routes web tool](https://coolroutes.sensableheatscapes.com/) (SHaDE Lab, Arizona State University).
It demonstrates the published method on a small, real sample of the ASU Tempe campus.
**It is not the full system and does not reproduce the paper's complete evaluation.**

## The method in one paragraph

Hourly mean radiant temperature (MRT) rasters are simulated with SOLWEIG on LiDAR-derived surface models.
For one raster, every edge of the pedestrian network is sampled once per map unit along its geometry
(`graph.py`): `mrt` is the mean of the samples and `cost` their **sum**. A route is a shortest path
(Dijkstra, `routing.py`) from the node nearest the origin to the node nearest the destination:
the **cool route** minimises `cost`, the **shortest route** minimises `length`. The tool returns both.

## What is included / excluded

| Included | Source in the lab's server |
|---|---|
| `src/coolroutes/graph.py`: network reading, projection, per-edge MRT sampling (`mrt`, `cost`) | `solweig_server/form_graphml.py` |
| `src/coolroutes/routing.py`: undirected graph, nearest node, cool vs. shortest route, statistics, GeoJSON | `server/routing.py`, `/api/route` in `server/server.py` |
| `src/coolroutes/raster.py`: raster sampling, WGS84 extent, the overlay colour ramp | `server/raster.py` |
| `data/`: 1 km sample window of two real MRT rasters and the campus walking network inside it | see *Data* |
| `tests/`, `run_demo.py`, `tools/make_sample_data.py` | new |

Same logic as the lab code, with one engineering change: the original builds the graph with OSMnx; this
release uses `networkx`, `geopandas`, `shapely` and `pyproj` only, so it installs easily.

**Not included:** the SOLWEIG implementation (`solweig_model/`, `solweig_mrt.py`). It is derived from
UMEP/SOLWEIG (Gothenburg Urban Climate Group, GPL-licensed), so it is referenced, not redistributed:
<https://github.com/UMEP-dev/UMEP>. Also left out: the hourly/daily job scheduler and the 72-hour forecast buffer,
the weather API client and its key, the Flask server, the React/ArcGIS front end, Docker/deployment files, and the
full-campus rasters (about 1.6 GB).

## Run it

```bash
pip install -r requirements.txt
python -m pytest              # 21 tests, about 15 s
python run_demo.py            # prints cool vs. shortest for 12 sample trips, rewrites the website demo assets
```

Minimal use:

```python
from coolroutes import *
raster = MrtRaster.from_geotiff("data/mrt_2024-04-26-2100.tif")
G = to_undirected(make_walking_network_graph(raster, "data/walk_graph_crop.gpkg"))
idx = NodeIndex(G)
a, b = (-111.9395, 33.4238), (-111.9368, 33.4192)          # (lon, lat)
cool = get_route(G, idx, a, b, "cost")[0]
short = get_route(G, idx, a, b, "length")[0]
```

## Tests (`tests/test_cool_routes.py`)

Run on the real sample data, for both rasters:

* edge `mrt` / `cost` equal an independent re-computation that uses rasterio's own sampler,
* `cost = mrt x number of samples` on every edge,
* weight `length` reproduces the true shortest path (checked against `scipy` Dijkstra),
* the cool route never has a higher summed heat cost or published average MRT than the shortest one (40 random pairs), and it finds a cooler alternative for most of them,
* route length consistency, nearest-node lookup vs. brute force, determinism,
* the committed golden routes (12 trips x 2 rasters x 3 weights, `data/golden_routes.json`) are reproduced,
* the colour ramp matches the legend, transparency and clipping rules.

The website demo re-implements the cost functions in JavaScript. `node demos/coolroutes/parity.test.mjs`
(from the portal root) checks that it returns the **same node sequences and statistics** as the Python golden routes.

## Data (`data/`)

| File | Provenance |
|---|---|
| `mrt_2024-04-26-2100.tif`, `mrt_2024-06-15-2200.tif` | 1000 x 1000 window (EPSG:3857, 1 px = 1 map unit, about 0.84 m on the ground) cut from the lab's hourly SOLWEIG MRT rasters. Stamps are **UTC** hours (the system names files with `tz_convert(None)`), i.e. **14:00 MST on 26 Apr 2024** and **15:00 MST on 15 Jun 2024** (Arizona is UTC-7, no DST). Stored as int16 x 0.01 degC (max rounding error 0.005 degC). |
| `walk_graph_crop.gpkg` | Sub-network (790 nodes, 1053 edges) of the campus walking network lying fully inside the window. Derived from OpenStreetMap data, (c) OpenStreetMap contributors, ODbL. |
| `reference_published_*.csv` | Per-edge `mrt` / `cost` from the live tool's own pre-computed graph for the same stamps, used only as a consistency check. |
| `golden_routes.json` | Regression target generated by `run_demo.py`. |

`tools/make_sample_data.py` documents exactly how these were cut from the full server data.

## Things we found while curating (please read)

1. **`average_mrt` in the live tool's API reads about 21 % high.** It is `sum(cost) / length`, but `cost` sums about
   1.2 samples per metre: the sampling step is one *EPSG:3857* unit (about 0.84 m on the ground at Tempe's latitude)
   while `length` is in true metres. Across the golden routes the ratio to a length-weighted mean is 1.21 to 1.22. The
   *ranking* of routes is unaffected. This release keeps the published field and adds `corrected_mean_mrt` (the
   commented-out `mrt * length` line of the original); the demo shows the corrected value.
2. **The pre-computed graph shipped with the server is not exactly reproducible from the shipped raster.** Per-edge
   values correlate only moderately (r about 0.6) with `reference_published_*.csv`, and 17 % of its edges use one or
   two fewer samples, although the aggregate MRT level agrees (48.3 vs 48.2 degC). It looks like it came from an
   earlier raster or pipeline version, so the tests assert structure and aggregate level against it, not per-edge equality.
3. The slider between "shortest" and "cool" in the website demo is a **demo extension** (`blended_weight`), not part of the live tool.

## Limitations

Two afternoon rasters over a 1 km window show how the method behaves. They say nothing about the accuracy of the
SOLWEIG MRT maps themselves (see the paper) or about full-campus routing statistics. Routes are only as good as the
MRT raster and the OpenStreetMap pedestrian network.
